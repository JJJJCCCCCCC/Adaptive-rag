# Adaptive‑RAG 下一轮实验设计

## 研究问题

按证据决定何时补检，能否在包含真实难点的电商政策题中，比固定单轮答全更多问题，并以更少 Token 达到与固定三轮相近的回答质量？现有 Evidence36 的独立复核为 **18/36 → 24/36 通过**，相对固定三轮为 **93 → 63 轮、90,834 → 83,931 Token（−7.6%）**。本轮保留该记录作为历史结果。[Evidence36 报告](25-evidence-guided-study.md)

## 题集与冻结

- 先用 24 道开发题检查题目歧义、基线配置、证据预算和评分表。开发题只参与调参和试运行。
- 正式留出集预定 120 道题，来自至少 12 套独立合成商户政策，每套包含容易混淆的商品档案、编号、条款与适用条件。预定分层为 30 道单文档题、40 道两文档题、30 道三文档题、10 道库内缺证据题、10 道域外题。两文档和三文档题中都要有不依赖显式编号的样本。
- 用独立答案和必需证据片段作为金标。评分前冻结题库、金标、评分说明、模型配置、三组代码提交和运行种子，保存哈希。题库在冻结前完成去重和泄露检查，正式跑完后保留全部样本和失败轨迹。
- 120 道是预定样本数，正式冻结前用开发题估计配对分歧和商户内相关性。如果主效应的检验功效不足，先扩充未见商户再冻结，公开最终样本规模及功效假设。

## 三组基线与机制消融

| 运行组 | 控制方式 |
| --- | --- |
| 固定单轮 | 执行共同首轮，使用首轮证据回答。 |
| 固定三轮 | 在同一首轮后继续至三轮，后两轮使用同样的补查生成规则。 |
| 证据自适应 | 证据足够或没有新的有效查询时停止，最多三轮。 |

主实验共享首轮路由、模型、共同首轮候选、查询上限、重排器、最终片段预算和回答提示。首轮检索轨迹按题复用，以减少基线噪声；独立端到端复验另行统计完整路由误拒、真实耗时与实际服务端用量。评分中保留检索前误拒及运行失败，区分质量错误和基础设施失败，并报告基础设施成功率。

另做小规模机制消融。将定向补查替换为仅按原问题改写，观察证据齐全率；将自适应停止改为固定三轮，观察节省主要来自哪类题。消融结果只用于解释主实验。

## 指标与判定

- **质量相对单轮。** 可回答题以数值、单位、适用条件和证据引用均正确计为答全。两位不知道策略的评审独立判分，分歧经第三人裁决。目标为 **提升至少 10 个百分点**，且以商户为聚类单位的配对 95% 置信区间下限高于 0。
- **效率相对三轮。** 同一批题的正式问答 Token 按服务端用量加总，包含路由、改写、判够、生成和核验，评审用量另计。目标为 **至少减少 20%**，**27.6%** 为进阶目标。自适应答全率相对固定三轮的配对 95% 置信区间下限须高于 **−5 个百分点**，否则只能报告成本与质量的权衡。
- **拒答与诊断。** 单列缺证据和域外组的正确拒答率，报告可回答题误拒率、证据齐全率、每题检索轮数、P50/P95 耗时和逐题胜负。规划目标包括 Evidence36 往后独立回归达到 **32/36 通过**；该旧题集回归指标与新留出集结论分开报告。
- **记录要求。** 每个题目和策略保存完整查询轨迹、最终引用、答案、盲评分、运行指纹及服务端 Token 回执。先汇总全部冻结样本，再展示代表案例。若只达到质量或成本其中一项，只报告该项。

## 同步验证其他项目的量化说法

- **Coder。** 用多种工具输出构造固定的成对输入，原始与压缩组保持同一系统提示、工具清单和模型。通过服务端 usage 同时报告总输入 Token 与扣除相同空载请求后的工具结果增量 Token，区分这两种分母。单列原文可恢复率、事实题通过率和裁剪后长度。**85%** 是待测目标，已有回归测得的指标是字符数。
- **FancyU。** 在独立合成数据库里比较重复提交前后的实际问卷、序列号与通知记录数。管理端 AI 另行记录实际转发给外部模型的字段，用 mock provider 捕获请求，扫描植入的邮箱、联系方式和凭据标记。保留 **11/11 规划用例、4/4 不安全请求拦截**的现有结果，将字段泄漏验证独立统计。

## 实验执行记录

Evidence120 的独立留出集包含 100 道可回答题。按证据补检通过 100 道，固定单轮通过 44 道。相对固定三轮，在答全数持平的情况下，检索轮数从 330 降到 220，Token 从 81,267 降到 46,069（−43.3%）。这是合成语料上的受控组件对照。[实验报告](../eval/benchmarks/evidence120/README.md)

实际采用确定性结构化打分和共用首轮检索轨迹，域外对照由商户范围检查处理。报告记录了与原方案的这些差异。Coder 实测增量输入 Token 减少 89.5%，整请求输入 Token 减少 85.2%。 [Coder 评测](https://github.com/JJJJCCCCCCC/coder/blob/main/benchmarks/compaction-report.md)
